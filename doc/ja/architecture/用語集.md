# 用語集

HarnessSeed のアーキテクチャ文書で使う言葉の**平易な定義**。型名や関数名は「代表シンボル」にまとめる。詳細は各章へ。

想定読者: ホストアプリに組み込む人、またはこのリポジトリを初めて読む人。

索引: [README.md](README.md) · English: [glossary.md](../../en/architecture/glossary.md)

---

## 製品・登場人物

### HarnessSeed

既存アプリに埋め込むための **エージェント実行エンジン（種＝seed）**。チャット UI そのものではない。ライブラリと CLI（`harness-seed`）を同じクレートで提供する。

- 詳細: [00_harness-seedの構造.md](00_harness-seedの構造.md)
- 代表: クレート `harness-seed`、`ReActLoop`

### ホスト

HarnessSeed を呼び出す側のアプリ（メール仕分け、開発エージェントなど）。ドメイン固有のルール・外部 API・チケット連携はホストが持つ。エンジンは特定製品名を知らない。

- 詳細: [04_ホスト拡張.md](04_ホスト拡張.md)

### ターン

ユーザーからの **1 回の依頼**に対する処理一式（記憶の注入 → 計画 → 実行 → 最終回答 → 日記など）。次の依頼は新しいターン。

- 代表: `ReActLoop::run_turn`、`TurnResult`

## 層（大まかな役割）

### 計画層

依頼を読み、**何をどの順でやるか（サブタスクの列）**を決める段階。ここではファイル操作などのツールは使わず、環境を書き換えない。

- 詳細: [01_計画層.md](01_計画層.md)
- 代表: `run_plan_layer`、`PlanArtifact`

### 実行層

計画に沿って **実際にツールを使い、作業を進めて回答する**段階。サブタスクごとに進む。

- 詳細: [02_実行層.md](02_実行層.md)
- 代表: `run_layer_loop`（exec）、`run_subtask_exec_audited`

### 記憶層

ターンの前後で、過去の作業や知識を **プロンプトに載せる／終了後に残す**仕組み。本体は外部 DB を直叩きせず、橋渡し口経由で読む・書く。

- 詳細: [03_記憶層.md](03_記憶層.md)
- 代表: Memory RAG、`MemoryBridge`、`recalled`、`diary`

## 実行の考え方

### ReAct（このリポジトリでの意味）

「考える →（必要なら）ツールを呼ぶ → 結果を見てまた考える」を繰り返すループ。計画層でも実行層でも同じ部品を使うが、計画層はツールなし・出力が計画、実行層はツールあり・出力がユーザー向け回答、と役割が違う。

- 詳細: [08_ReAct実装.md](08_ReAct実装.md)、[10_最少行動単位.md](10_最少行動単位.md)
- 代表: `run_layer_loop`、`AgentStep`

### サブタスク

計画が切り出した **小さな作業単位**（目標と完了条件を持つ）。実行層はこれを順に（または依存関係に従って）処理する。

- 代表: `Subtask`、`PlanArtifact.subtasks`

### タスクレジストリ

あらかじめ JSON で定義した **定型作業契約**（使うツールの順・引数の型など）の置き場。計画が契約タスクを指すと、LLM 任せより機械的な「ステップドライバ」で走らせられる。

- 詳細: [05_タスクレジストリ.md](05_タスクレジストリ.md)
- 代表: `tasks/*.json`、`TaskRegistry`

### ステップドライバ

契約タスクを、LLM に毎回選ばせず **決まった手順どおり**にツール実行する方式。失敗や引数ずれは監査で検知する。

- 詳細: [02_実行層.md](02_実行層.md)、[05_タスクレジストリ.md](05_タスクレジストリ.md)
- 代表: `run_subtask_driver`、`ArgAuditMode`

### 監査

「契約どおりのツールが呼ばれたか」「引数は足りているか」を実行後に機械的に検査すること。未達なら同じサブタスクをやり直すことがある。

- 代表: `audit_trace`、`TaskExecutionAudit`

### two_phase

**計画してから実行する**標準のターン進行（計画 → サブタスク実行の二段）。

- 詳細: [00_harness-seedの構造.md](00_harness-seedの構造.md)
- 代表: 設定 `react.two_phase`、`run_turn_two_phase`

### 推進ループ（advance）

長い依頼を **複数フェーズ**に分け、終わったフェーズの要約を次のプロンプトに載せて続ける外側の進行。`two_phase` に似るが、フェーズ間の引き継ぎが厚い。

- 詳細: [07_推進ループ.md](07_推進ループ.md)
- 代表: 設定 `react.advance`、`run_turn_advance`

## 記憶まわりの語

### recalled

今回のターンで LLM に見せる **思い出した断片**（作業ログや検索ヒットなど）を載せる場所。プロンプトの一部になる。

- 詳細: [03_記憶層.md](03_記憶層.md)、[09_コンテキストマッピング.md](09_コンテキストマッピング.md)
- 代表: `PromptBlocks.recalled`

### diary

ターン終了後に残す **作業の記録**（要約・回答など）。次ターン以降の「最近の作業」の材料になる。

- 代表: `MemoryBridge::diary`、`DiaryEntry`

### MemoryBridge

外部記憶バックエンド（ローカル日記、mempalace など）への **読み書きの口**。エンジン本体は製品固有 API を直接呼ばない。

- 代表: `MemoryBridge`、`LayeredMemoryBridge`

## ホスト連携の語

### hook（ライフサイクル hook）

エンジンがターン進行の決まった地点で呼ぶ **ホスト向けコールバック**。本筋の計画・実行は変えず、チケット起票などの副作用だけを載せる。

- 詳細: [04_ホスト拡張.md](04_ホスト拡張.md)（「hook とは何か」）
- 代表: `TurnLifecycle`

### TaskTracking

PM／チケット連携向けに整えた **開始・完了の業務 API**。生の hook よりこちらを実装するのが推奨。

- 代表: `TaskTracking`、`lifecycle_from_tracking`

### HostScratch

1 ターン分のホスト専用の袋（JSON）。チケット ID などを置く。**LLM のプロンプトには載せない**。

- 代表: `HostScratch`、`HostView`

### RunStatus / outcome

サブタスクやターンが **成功・失敗・取消**のどれで終わったかを表す構造。hook の完了通知に付く。

- 代表: `RunStatus`、`SubtaskOutcome`、`TurnOutcome`

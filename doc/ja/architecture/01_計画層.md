# 計画層


ユーザーの依頼を読み、何をどの順でやるか（サブタスクの列）を決める段階である。依頼をそのまま実行に投げると手順が曖昧なままツールを乱発しやすいので、先に作業単位と完了条件を固める。ここではファイル操作などのツールは使わず、環境も書き換えない。

標準の two_phase ではこの層を通る。ホストが計画を全部供給するなら、エンジン側の計画 LLM は薄くてよい。流れは、依頼を受けてサブタスク列と要約を出し、実行層へ渡す（知識だけで足りるときは実行をスキップすることもある）。実装は ReAct 派生ループ（`run_plan_layer`）、出力は `PlanArtifact`。

## 1. 計画層の位置づけ

```mermaid
flowchart LR
    IN["プロンプト受取<br/>user_input"] --> PLAN["計画層<br/>run_plan_layer"]
    PLAN --> PARSE["Harness パース<br/>parse_harness_strict"]
    PARSE --> HS["HarnessState<br/>PlanArtifact"]
    HS --> EXEC["実行層へ"]
```

まず依頼を受け、計画層が必要な作業と完了条件を考える。この時点の出力はまだ LLM が作った文章なので、そのまま実行には渡さない。

次にエンジンが出力を検査して、実行に必要な形へ直す。解釈できた計画だけが次の層へ進み、解釈できない出力は計画として扱わない。こうして実行層は、自由な文章ではなく構造化された作業一覧を受け取る。

| 項目 | 計画層 | 実行層 |
|------|--------|--------|
| 頭脳 | `PlanBrainMode` | exec `BrainMode` |
| ループ | `run_plan_layer` | `run_layer_loop`（exec） |
| ツール | **不可** | **可** |
| 出力 | `PlanArtifact` | ユーザー向け `Answer` |
| 副作用 | **なし** | **あり** |

計画層は、何をするかを決めるだけで環境を変えない。実行層は、その決定を受けて初めてツールを使い、得られた結果をユーザーへ返す。

この違いにより、計画の出力は後続処理のための成果物になり、実行の出力は会話の返答になる。頭脳やループの名前は実装の差し替え点だが、層を分ける本質は副作用を許すかどうかである。

**原則**: 計画層が設計するのは **手順（PROCEDURE）だけ**。データの読み元（INPUT）と書き込み先（OUTPUT）はホストが固定し、LLM は変更しない。

## 2. 処理フロー

```mermaid
flowchart TD
    START["run_turn / run_plan_preview"] --> MEM["Memory RAG 注入<br/>work_log / knowledge"]
    MEM --> SKIP{"PlanDataContract<br/>.skip_plan_layer?"}
    SKIP -->|はい| TRIV["skip_execution 計画を合成<br/>LLM 呼び出しなし"]
    SKIP -->|いいえ| CAND["候補選定 summary→candidates"]
    CAND --> REG["候補をコンテキスト登録"]
    REG --> LOOP["run_layer_loop<br/>LayerLoopOptions::plan"]
    LOOP --> BRAIN["PlanBrainMode::decide<br/>Thought / Recall / Answer"]
    BRAIN -->|Action| REJ["Observation: tools not available"]
    REJ --> BRAIN
    BRAIN -->|Recall| MEM2["知識チャネル search"]
    MEM2 --> BRAIN
    BRAIN -->|Answer| PARSE["parse_harness_strict"]
    LOOP -->|answer 未達| FIN["強制 answer 要求<br/>失敗時 single_subtask"]
    FIN --> PARSE
    PARSE --> KS["knowledge_sufficient ゲート"]
    KS --> RESOLVE["TaskRegistry::resolve_plan"]
    RESOLVE --> APPLY["apply_harness_from_plan<br/>PromptBlocks へ反映"]
    TRIV --> APPLY
    APPLY --> OUT["PlanArtifact → 実行層 or 直接応答"]
```

最初にターン開始時の記憶を載せ、計画を作る必要があるかを決める。不要な軽い会話なら、LLM を呼ばずに直接応答できる計画を作る。

通常の依頼では候補をそろえてから計画ループに入る。ループ中は考えることと知識を追加で探すことはできるが、環境を変える操作は拒否される。

答えが得られたら、エンジンが計画として読み取り、知識だけで実行を省略してよいかを確かめる。最後にタスク契約と照合して実行用の文脈へ反映し、実行するか直接答えるかへ進む。

### 2.1 エントリポイント

| API | 用途 |
|-----|------|
| `run_plan_layer` | 計画層ループ + Harness パース（`layer.rs`） |
| `run_plan_preview` | 計画のみ実行、実行層には進まない（`react.rs`） |
| `run_turn_two_phase` / `run_turn_advance` | 計画層のあと実行層へ直列接続 |

### 2.2 計画層スキップ

`PlanDataContract::skip_plan_layer()` が `true`（挨拶・雑談など `skip_execution: true` の trivial chat）のとき、LLM を呼ばず即座に以下を合成する。

```rust
PlanArtifact {
    summary: "direct chat".into(),
    skip_execution: true,
    subtasks: vec![],
    knowledge_sufficient: Some(true),
}
```

## 3. ReAct ループ（plan モード）

計画層も `run_layer_loop` を使うが、`LayerLoopOptions::plan` により実行層と区別される。

| 設定 | 値（plan） |
|------|------------|
| `tools_enabled` | `false`（`recall` のみ記憶読み取り可） |
| `context_label` | `"plan"` |
| `max_thoughts` | 1 |
| `max_steps` | `react.max_steps_plan`（既定 **4**。長く探索しない） |

計画ループは短い。足りない証拠は実行層で集める。`answer` 未達時は一度だけ妥当な計画の出力を要求し、それでもダメなら `single_subtask(ユーザ要求)`（詳細は [memory.md](03_記憶層.md) §3）。

### 3.1 `knowledge_sufficient`

計画 JSON に含める。`skip_execution: true` は **`knowledge_sufficient == true` のときだけ**許可。薄い Recalled だけで最終回答させないための機械的ゲート。

```mermaid
sequenceDiagram
    participant U as ユーザー入力
    participant L as run_layer_loop
    participant P as PlanBrainMode
    participant H as parse_harness_strict

    U->>L: TurnPromptContext
    loop max_steps_plan
        L->>P: decide
        alt Thought
            P-->>L: 内部推論（副作用なし）
        else Action（拒否）
            P-->>L: "plan layer: tools are not available"
        else Answer
            P-->>L: 作業指示書（JSON or テキスト）
        end
    end
    L->>H: Answer 本文
    H-->>L: HarnessState
```

計画ループは、限られた回数だけ次の一手を考える。内部で考えるだけなら記録して続けられ、追加の知識が必要なら読み取り専用の経路を使える。

一方で、ツールを使おうとする出力は実行されず、拒否された事実が返る。最終的に計画の答えが出たときだけ、その本文を構造化して後続の処理に渡す。

LLM が返すステップ形式（`PlanBrainMode` / `PLAN_REACT_SYSTEM_CORE`）:

```json
{"step":"thought","content":"<reasoning>"}
{"step":"answer","content":"<作業指示書>"}
```

`Action` / ツール呼び出しは Observation で拒否される。

## 4. Planner 固定ゾーン（プロンプト構成）

計画層の LLM プロンプトは **Planner 固定ゾーン** + ユーザーゴール + 計画 trace で構成される（`plan/prompt.rs`）。

```mermaid
flowchart TB
    subgraph system["system"]
        CORE["PLAN_REACT_SYSTEM_CORE"]
        RULES["Additional rules"]
        REC["Recalled context"]
        CONTRACT["PlanDataContract<br/>INPUT / OUTPUT 境界"]
        TOOLS["tool_catalog（参照のみ）"]
        SKILLS["task catalog（skills）"]
        RT["Execution environment"]
    end
    subgraph user["user"]
        SESS["SessionMemory（直近ターン）"]
        GOAL["ゴール: user_input"]
        TRACE["Plan trace so far"]
    end
    system --> LLM["PlanBrainMode"]
    user --> LLM
```

まず変わりにくい制約や利用可能な情報を system 側に置く。ここには、入力・出力の境界や参照用のカタログも含まれるが、計画層はそれらを実行する権限を持たない。

次に今回の依頼、直近の会話、途中までの計画を user 側から渡す。モデルは両方を合わせて、固定された入出力の間でどんな手順を組むかだけを決める。

ホスト（アプリ）が `PromptBlocks` に載せる主なブロック:

| ブロック | 役割 |
|----------|------|
| `plan_data_contract` | INPUT（read）/ OUTPUT（write）の固定境界 |
| `plan_task_catalog` | 登録タスク一覧（skills） |
| `tool_catalog` | ツール定義（計画層では実行不可・参照用） |
| `recalled` | 参照メール等の長文コンテキスト |
| `rules` | 追加ルール |

## 5. データ契約（INPUT / PROCEDURE / OUTPUT）

`PlanDataContract`（`plan/contract.rs`）は 1 ターン分の read / write を LLM に推測させない。

```mermaid
flowchart LR
    IN["INPUT（read）<br/>ホスト固定"] --> PROC["PROCEDURE<br/>PlanArtifact.subtasks<br/>LLM が設計"]
    PROC --> OUT["OUTPUT（write）<br/>ホスト固定"]
```

最初にホストが、読んでよい入力と書いてよい出力を決める。これはアプリの権限と画面の都合に関わるため、計画モデルには変更させない。

その二つの境界の間で、計画層は作業の順番と完了条件を作る。したがって、モデルが設計するのは手順だけであり、データの出所や送付先を推測して置き換えることはない。

| 層 | 例 | 誰が決める |
|----|-----|-----------|
| **INPUT** | `UserMessage`, `ImapEmail { uid }`, `LocalMailDb` | ホスト |
| **PROCEDURE** | サブタスク列、`task` id、`goal`, `done_when` | **計画層 LLM** |
| **OUTPUT** | `ChatOnly`, `ComposeForm`, `MailDb` | ホスト |

契約はプロンプトに `format_for_planner()` で展開され、LLM には「INPUT からだけ読み、OUTPUT にだけ書け、間の手順だけ設計せよ」と指示される。

## 6. 計画のパース（Harness パース）

Planner の `Answer` 本文は `parse_harness_strict`（`harness/parse.rs`）で `HarnessState` に変換される。

```mermaid
flowchart TD
    RAW["Planner Answer 本文"] --> JSON{"JSON 計画?"}
    JSON -->|はい| PA["PlanArtifact"]
    JSON -->|いいえ| NUM{"番号付き行<br/>2 行以上?"}
    NUM -->|はい| PA
    NUM -->|いいえ| PLAIN{"平文?"}
    PLAIN -->|はい| PASS["PlanArtifact::passthrough<br/>skip_execution: true"]
    PLAIN -->|いいえ| ERR["PlanParseFailed"]
    PA --> HS["HarnessState"]
    PASS --> HS
```

まず本文が JSON の計画として読めるかを試す。読めれば、サブタスクを含む計画として状態に入る。

JSON でなければ、複数行の番号付き手順を次に受け付ける。それにも当てはまらない平文は、作業を組まずに直接答える経路として扱う。どの形にも解釈できない場合だけ、計画のパース失敗として止める。

### 6.1 受け付ける計画 JSON 形式

**形式 A** — `PlanArtifact` 直接:

```json
{
  "summary": "…",
  "skip_execution": false,
  "subtasks": [
    { "id": 1, "task": "list_dir", "params": {"path": "src"}, "goal": "…", "done_when": "…" }
  ]
}
```

**形式 B** — フロー形式（`input` / `steps` / `output`）:

```json
{
  "input": ["read: user_message"],
  "steps": [
    { "id": 1, "task": "web_research", "params": {"query": "…"}, "goal": "", "done_when": "" }
  ],
  "output": "write: chat_only",
  "skip_execution": false
}
```

パース失敗時は JSON 修復・複数 JSON オブジェクト抽出（`extract_json_objects`）を試みる。

### 6.2 PlanArtifact の意味

| フィールド | 説明 |
|------------|------|
| `summary` | 計画の要約 |
| `skip_execution` | `true` なら実行層を省略し直接応答 |
| `subtasks` | 直列実行するサブタスク列（id は 1 始まり・一意） |

`needs_execution()` = `!skip_execution && !subtasks.is_empty()`

### 6.3 HarnessState

パース後の内部状態。実行層・プロンプト注入に使われる。

| フィールド | 説明 |
|------------|------|
| `work_instructions` | Planner 生テキスト |
| `plan` | パース済み `PlanArtifact` |
| `current_step` / `total_steps` | 実行進捗 |
| `tool_set` | 現在ステップのツール制限 |
| `references` | 参照文書（メール等） |
| `status` | `Ready` / `Executing` / `Completed` / `Aborted` |

## 7. 計画後の反映

`apply_harness_from_plan`（`react.rs`）が計画結果を実行層向けプロンプトへ載せる。

1. `TaskRegistry::resolve_plan` — タスク id の正規化・契約との整合
2. `blocks.work_instructions_text` — 作業指示書テキスト
3. `harness.begin_execution()` — サブタスクありなら `status = Executing`
4. `sync_harness_step_to_blocks` — 現在ステップ説明を `current_step_text` へ

参照情報（`HarnessReference`）は計画開始前に `recalled` へ載せ、Harness にもマージされる。

## 8. PlanBrainMode（頭脳）

| モード | 用途 |
|--------|------|
| `Rule(RulePlanBrain)` | `--no-llm` / ルールのみ。help・echo は即 `skip_execution` |
| `Llm(PlanLlmBrain)` | 本番 LLM。タスクカタログ付きプロンプト |
| `Mock` | 統合テスト用 |

ルール頭脳の典型フロー:

1. 初回 `Thought`（「依頼をサブタスクに分解する」）
2. 次ステップで `Answer`（単一サブタスク JSON）

## 9. skip_execution 時の分岐

計画層完了後、`PlanArtifact::needs_execution()` が `false` のとき:

```mermaid
flowchart LR
    PLAN["計画層完了<br/>skip_execution: true"] --> SINGLE["run_turn_single<br/>元入力で exec ReAct"]
    SINGLE --> END["TurnResult"]
```

計画が実行不要と認められた場合、サブタスクの列は回さない。代わりに元の依頼を一度だけ実行用の頭脳へ渡し、ユーザー向けの返答を作る。

これは無条件の近道ではない。知識が十分だと確認された計画、または直接応答として扱う計画だけがこの枝に入り、返答後は通常どおり `TurnResult` で終了する。

## 10. 設定項目

| キー | 既定 | 計画層への影響 |
|------|------|----------------|
| `react.max_steps_plan` | `4` | 計画 ReAct の最大ステップ |
| `react.two_phase` | `true` | オフ時は計画層自体をスキップ |
| `react.show_plan` | `true` | `PlanArtifact` を stdout 表示 |
| `react.show_prompt` | `false` | 計画層プロンプトを stderr 表示 |
| `llm.*` | — | `PlanLlmBrain` のコネクタ設定 |

## 12. まとめ

- 計画層は **サブタスク列（作業指示書）を設計する**だけで、ツールは使わない。
- ReAct ループは実行層と共通だが `tools_enabled: false`。
- INPUT / OUTPUT はホスト固定、LLM が設計するのは **PROCEDURE（subtasks）** のみ。
- Planner 出力は JSON・番号付きテキスト・平文 passthrough の順でパースされる。
- `skip_execution` なら実行層を省略し、exec 頭脳が直接応答する。
- パース結果は `HarnessState` として実行層プロンプト（作業指示書・現在ステップ）に引き渡される。

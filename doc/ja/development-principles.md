# 開発方針

HarnessSeed 本体・アダプタ・エージェント向け機能を変更するときの原則。

## 解説はわかりやすさを欠かさない

**仕様や設計を書くとき、いちばん端折られやすいのが冒頭の概要である。**

概要はチェックリスト見出しではなく、普通の文章で書く。そのなかに次が読み取れること。

- それは何か（型名・ファイル名の前に、製品目線の定義）
- 何のためにリポジトリにあるか（無いと困ること、意図的にやらないこと）

設定キーの表だけで動機を済ませない。読者が概要だけで「なぜこの部品があるか」に答えられること。

**図と表は、本文の一部として説明する。** 「次の図は〜である」で切って解釈を読者に委ねない。図のあとに、何が起きているか・どこで分かれるか・何が同じで何が違うかを、普通の文で続ける。表も同様に、対比や一覧の意味を本文で言い切る。

つなぎに「図に示すように」「表に示すように」を使ってよいが、**箱名・型名・関数名を一息でなぞるだけにしない。** まず平易な言葉で段階を説明し、実装名は必要になったときだけ出す。一図の内容を一文に圧縮しない。

「読みどころ」「読み方はこう」のような、図・表の読み方を教えるメタな言い回しは使わない。

## 汎用解を常に優先する

**個別の事例だけを解決するロジックは価値が低い。**

- 再現に使ったユーザ発話（例: 「このプロジェクトについて説明して」）は**検証シナリオ**であり、その文言やドメイン専用の分岐・既定手順をコードに埋め込まない。
- 設計するときは「メールでも Web でもコーディングでも同じ形で効くか」を問う。効かないなら、その事例用の特例ではなく、層の責務（記憶 / 計画 / 実行）に載る**一般的なゲートや契約**に落とす。
- ハードコードしてよいのは、ドメイン非依存の機械的制約だけである（例: 根拠不足なら `skip_execution` を拒否する、両方チャネル同時 ON なら知識側を優先する）。特定パス・特定タスク id・特定プロダクト名を既定手順にしない。
- プロンプトやルールに書く方針も同様に汎用語で書く。「README を読め」ではなく「足りない証拠は利用可能なツールで集めよ」。

## 層の責務を混ぜない

| 層 | やること | やらないこと |
|----|----------|--------------|
| 記憶 RAG | 作業ログと知識の分岐、候補の取得 | ドメイン手順の決定 |
| 計画 | 根拠が足りるかの判断、手順の列挙 | 特定ユースケース専用の固定レシピ |
| 実行 | カタログ上のツール選択と実行 | 記憶経路の再発明 |

ある失敗を直すとき、まず「どの層の一般契約が破れているか」を特定する。ログ上の一発話だけが通るパッチは採用しない。

## 検証と実装の分離

- ログ検証は具体シナリオでよい。
- 実装はシナリオ名をコードに残さない（関数名・コメント・既定 goal に特定ドメインを書かない）。
